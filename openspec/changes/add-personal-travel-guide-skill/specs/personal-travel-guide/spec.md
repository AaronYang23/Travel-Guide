# Spec Delta

## Purpose

为个人旅行规划提供可迭代的对话体验：目的地未定时根据当次旅行画像推荐候选地，用户确认后生成完整攻略；目的地已定时从已知信息生成草案，并在反馈中逐步确定取舍、修订行程和管理长期偏好。

## ADDED Requirements

### Requirement: 逐步明确旅行条件
Skill SHALL 区分本次旅行条件、已确认的长期偏好和未知信息。目的地未定时，Skill MUST 围绕出行时间、天数、出发地、人数、预算、交通方式、旅行类型、节奏和不喜欢的地点收集当次画像；已提供的内容不重复追问，未确定的偏好不得推断成已确认事实。

#### Scenario: 条件不完整但可以先规划
- **WHEN** 用户提供目的地和大致游玩天数，但没有给出预算或所有兴趣偏好
- **THEN** Skill 先给出可讨论的行程草案，注明预算和偏好方面的假设，并提出下一项最有助于修订的具体问题

#### Scenario: 打开去哪玩但未确定目的地
- **WHEN** 用户提出“去哪玩”且没有确定目的地
- **THEN** Skill 询问尚未知晓的出行时间、天数、出发地、人数、预算、交通方式、旅行类型、节奏和不喜欢的地点，为旅行类型提供人文、古镇、自然、城市、美食等可多选类别，而不是要求用户先指定目的地

#### Scenario: 用户暂时说不清全部偏好
- **WHEN** 用户只回答了一部分画像问题，或表示某些喜好尚未确定
- **THEN** Skill 保留已知条件、标记未知项，并只补问当前阻碍推荐的关键信息，不把未回答项写成固定偏好

### Requirement: 推荐可比较的候选目的地
Skill SHALL 在获得足以确定出发范围、时间和旅行倾向的信息后，结合本次画像给出按匹配程度排列的候选目的地 Top N。每个候选 MUST 说明契合的体验、交通与时间可行性、预算取舍及不适合的因素；用户给出的单程最长时间 MUST 作为筛选约束，而没有可靠依据的耗时或费用 MUST 标为待核实。

#### Scenario: 根据画像推荐候选
- **WHEN** 用户给出出发地、旅行时段和天数、人数、预算、交通方式、偏好类型、节奏以及回避项，尚未选择目的地
- **THEN** Skill 给出一组可比较的候选目的地及各自的匹配理由和取舍，等待用户选择或确认，而不直接生成某一候选的完整攻略

#### Scenario: 给定单程时长上限
- **WHEN** 用户指定可接受的单程最长时间
- **THEN** Skill 不将已知超过上限的地点当作符合约束的候选，无法核实耗时时明确标注不确定

#### Scenario: 没有符合约束的候选
- **WHEN** 已知条件下找不到足够可信且满足约束的目的地
- **THEN** Skill 说明限制冲突或信息缺口，询问用户希望调整哪项条件，不编造符合要求的目的地

### Requirement: 依据确认的目的地生成可修订攻略
Skill SHALL 在用户已给定目的地或已选择、确认候选地后，根据当前旅行条件与已确认偏好组织每天的活动顺序、地点选择和必要的交通衔接，覆盖行程、吃、住、玩；对于未给出的信息 MUST 明示假设，不得将推断描述成用户已经确认的偏好。

#### Scenario: 生成初稿
- **WHEN** 用户给出足以确定目的地和行程长度的信息并请求攻略
- **THEN** Skill 输出按天组织的可讨论路线与吃、住、玩建议，说明主要取舍与待确认假设，不因偏好尚未穷尽而拒绝生成

#### Scenario: 选择候选后生成完整攻略
- **WHEN** 用户从候选目的地中选择或确认一处
- **THEN** Skill 根据已收集的本次画像生成该地的行程、吃、住、玩攻略，并保留尚待核实的时效信息标记

#### Scenario: 反馈后局部修订
- **WHEN** 用户对已有草案表示希望减少赶路或调整某类活动的比重
- **THEN** Skill 保留未受影响的已确认条件，修订相关行程并说明关键变化，同时继续允许后续反馈

### Requirement: 长期偏好需经确认才保存
Skill SHALL 在本次对话中使用用户表达的偏好，但 MUST 仅在用户明确要求长期保留或确认保存时更新持久偏好资料；一次性条件和未经确认的假设不得自动写入长期偏好。

#### Scenario: 当前行程偏好不自动持久化
- **WHEN** 用户说本次旅行想住在车站附近或这次不安排博物馆
- **THEN** Skill 将其用于当前行程，但不自动保存成今后所有旅行的固定偏好

#### Scenario: 明确要求记住
- **WHEN** 用户明确要求记住今后尽量不安排清晨出发
- **THEN** Skill 将这项偏好记录到持久偏好资料，后续规划会读取并应用它

#### Scenario: 偏好变更
- **WHEN** 用户明确要求修改或删除此前保存的偏好
- **THEN** Skill 更新对应记录，不继续把旧偏好当作有效约束

### Requirement: 区分已核实信息与待核实信息
Skill MUST 对开放时间、门票、价格、交通班次等可能变化的信息区分已核实与待核实状态；使用可用来源核实后 SHALL 给出来源或查询依据，不可用时不得宣称实时准确。

#### Scenario: 没有可用实时信息来源
- **WHEN** 当前环境无法查询某个景点的当日营业时间或交通班次
- **THEN** Skill 标注该信息待核实，并指出出行前需要确认的具体事项，不捏造来源或精确数值

#### Scenario: 可以核实实时信息
- **WHEN** 当前环境有可用的信息查询工具且用户需要具体时效数据
- **THEN** Skill 使用可用来源核实关键数据，并在攻略中标注查询依据及仍未核实的部分

### Requirement: 行程输出不触发外部动作
Skill SHALL 默认在对话中提供和修订攻略；未经用户另行明确要求，不得预订服务、发布内容或将单次行程自动保存到项目文件。

#### Scenario: 仅请求行程建议
- **WHEN** 用户要求一份旅行攻略而未要求执行预订或保存文件
- **THEN** Skill 在对话中返回攻略，不创建预订、不发布内容，也不写入单次行程文件
